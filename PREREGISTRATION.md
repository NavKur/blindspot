# Blindspot pre-registration

**Committed before any exam results existed.** The git commit timestamp of this file is the proof.
Any change after that commit is listed under *Deviations* at the bottom, with a reason. Results are
reported as they come out, including null results.

## 1. Question

Does Bob understand the tinydb codebase better when given targeted context written from its own
measured blind spots (Blindspot's Cartographer) than when given the `AGENTS.md` produced by Bob's own `/init`?

## 2. Materials

- **Codebase:** tinydb `v4.9.0`, commit `1e39ad3a2d9eca57efd9019fd089b5a04676da95` (see `target.lock.json`).
  Only the `tinydb/` package is examined.
- **Examinee:** IBM Bob Shell (`bob run --format json`), custom mode `blindspot-examinee`, closed-book:
  `--disable-tool-groups read,edit,command,browser,mcp --disable-mcp --disable-subagents`.
  Verified by the go/no-go test (`results/gonogo.json`): 0 tool calls, file contents not visible, `AGENTS.md` visible.
- **Questions:** generated by a script from the code's syntax tree (no AI), so every answer is checked
  automatically. Families: imports, existence (half real names, half near-miss fakes), defaults, raises, calls.
  True/false questions are balanced 50/50.

## 3. Conditions

| Condition | Context files in the target during the exam |
|---|---|
| C0 | none |
| C1 | `AGENTS.md` generated by Bob `/init` on the pinned target |
| C2 | C1 plus `.bob/rules/blindspot-<module>.md` written by the Cartographer mode |

Everything else (mode, flags, prompt template, batch size, question order within a batch) is identical across conditions.

## 4. Design

- One exam of `N_TRAIN + N_TEST` questions, generated and split with seed `SEED`, stratified so every module appears in both sets.
- **TRAIN** is sat once under C1. Its results produce a per-module failure summary.
- **Cartographer** receives only that TRAIN summary plus read access to the red modules' source.
  It never sees TEST questions or answers. It writes context for at most `MAX_CARTO_MODULES` modules.
  If no module is red on TRAIN, it writes for the `MAX_CARTO_MODULES` modules with the highest confidently-wrong rate.
- **TEST** is sealed until the final run, then sat under C0, C1 and C2, `REPEATS` times each.
- The generator, prompts and thresholds are frozen (git tag `freeze`) before the final TEST runs.

## 5. Outcomes and analysis

**Marking.** An answer is correct if it matches the truth exactly (booleans; literal values compared after
`ast.literal_eval` normalisation). Each answer carries a stated probability `p` that it is correct.

**Primary endpoint.** TEST accuracy, C2 vs C1, repeat 1.
**Primary test.** Exact McNemar test on discordant question pairs, two-sided, alpha = `ALPHA`.
**Hypothesis.** C2 accuracy > C1 accuracy. A significant result in the other direction is reported as such.

**Secondary (Holm-corrected across the three):**
1. C1 vs C0 accuracy (does `/init` help at all?), McNemar, repeat 1.
2. Brier score C2 vs C1, paired bootstrap (2,000 resamples of questions), repeat 1.
3. Confidently-wrong rate C2 vs C1, McNemar on the per-question indicator (wrong and `p >= CONFIDENT_P`), repeat 1.

**Descriptive (no tests):** per-module accuracy with Wilson 95% intervals; reliability diagram (5 bins) and ECE;
run-to-run agreement across the `REPEATS` runs per condition; coins per call by condition.

**Sensitivity check: cluster bootstrap.** Questions about the same piece of code are not independent
(if Bob misunderstands one function, several answers fail together), so the question-level analysis may be
too optimistic. For the C2 minus C1 differences in accuracy and in Brier score (repeat 1), we resample whole
clusters of questions with replacement, `N_BOOT` times, and report the 95% percentile interval and the
design effect (cluster variance divided by independent-question variance).
- Primary clustering: the code entity each question is about (function, method or class; module-level
  questions form one cluster per module). This gives many clusters, which the bootstrap needs.
- Secondary clustering: module. tinydb has about 9 modules, too few for a reliable cluster bootstrap,
  so this is shown for transparency only.
- If the entity-clustered interval for the accuracy difference includes 0 while the primary McNemar test
  is significant, this is stated next to the primary result. It does not replace the primary result.

**Red module rule.** A module is red if the Wilson 95% lower bound on its accuracy is below `RED_ACC_LOWER`,
or its confidently-wrong rate (share of its questions answered wrongly with `p >= CONFIDENT_P`) exceeds `RED_CW_RATE`.

## 6. Exclusions and data quality

- Any answer from a call that reports one or more tool calls is excluded (closed-book violated) and the count is reported.
- Missing or unparseable answers are excluded and counted. A batch with more than 10% missing is re-run once;
  the re-run replaces it and this is logged.
- No other exclusions. No question is removed after seeing results.

## 7. Power, stated honestly

With 200 paired TEST questions, the McNemar test has reasonable power only for differences of roughly
8 to 10 percentage points or more, depending on how many answers change between conditions. Smaller true
effects may not reach significance. A null result is reported as a finding (it would agree with
*Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?*, ETH Zurich SRI Lab, 2026, arXiv 2602.11988).
